# timeplan

Answers "how long will this take" with numbers measured on this machine instead of a guess.

An agent estimates time from human work, and that is wrong in both directions at once. The agent part of a job
is usually minutes. Tool time, human gates and queue wait are usually hours. None of them scale like a person.
So the numbers here are measured from real sessions, and the agent is only allowed to size the work.

Fed from two transcript stores, Claude Code in `~/.claude/projects` and pi in `~/.pi/agent/sessions` (override with
`TIMEPLAN_CLAUDE_ROOT` and `TIMEPLAN_PI_ROOT`). Both record output tokens, request durations and tool durations.
Measured on 2026-11-21: 1,150 transcripts, 69M output tokens, 222h of API time.

```
$ timeplan.py estimate -m opus --out 30000 --tools "bash:8 read:20 edit:6" --gates 1
estimate #1 · claude-opus-5-5 · 30,000 output tokens · 34 tool calls = 33 requests · 1 agent
  model     2s first request + 32 ×    4s =   1m 57s  +  30,000 tok ÷ 130 tok/s =   3m 50s   (5m 47s)
  tool        8 × Bash           530ms =       4s   (p90 2m 14s)
  tool        6 × Edit           270ms =       2s   (p90 28s)
  tool       20 × Read            80ms =       2s   (p90 11s)
  waiting   1 × 5s human gate =       5s
  ----------------------------------------------------------------------
  agent     ~6m 40s   range 2m 36s to 10m 23s
  human     1,500 tok/h means 20h of one person   (180× slower than the agent)
```

Two clocks, always. Six minutes of agent time, twenty hours of a person. Neither number is the other.

## What it is, and what it is not

It is a measurement plus a calculator. `calibrate` reads transcripts and fits a rate per model. `estimate` turns
tokens and tool calls into wall clock. `schedule` adds up a plan of several steps, because that sum is where most
plans go wrong. `done` records what really happened and corrects the next estimate.

It is not a benchmark. Nothing here is comparable to another machine, another provider or another scaffold. The
numbers describe this box.

It is not a promise. Agent time is not delivery time. A six-minute job still waits for whatever review you put in
front of it.

It is not a model of cost. Tokens are counted because they take time, not because they cost money.

## Quick start

Python 3.10 or newer, standard library only, no network.

```
git clone https://github.com/AutismLLM/skills.git
cd skills/timeplan
python3 timeplan.py calibrate     # 35s first time, 0.3s after; writes data/rates.json
python3 timeplan.py show          # the measured table
python3 timeplan.py estimate -m sonnet --lines 300 --tools "bash:10 read:20"
```

To let an agent find it on its own, link the folder into the skill directory of the agent you use:

```
ln -s "$PWD" ~/.claude/skills/timeplan
ln -s "$PWD" ~/.pi/agent/skills/timeplan
```

Run those from `skills/timeplan`, the folder that holds `SKILL.md`.

The repository ships no `data/rates.json` on purpose. Rates describe one machine, so the first run is `calibrate`.

## Commands

| Command | What it does |
|---|---|
| `calibrate [--source claude\|pi\|all] [--full]` | scan transcripts, fit rates per model, write `data/rates.json` |
| `show [--json]` | model table, tool latencies, turn sizes, per-source counts |
| `estimate -m <model> (--out N \| --lines N \| --turns N) [--tools "bash:6 read:20"] [--gates N] [--parallel N] [--json]` | one piece of work |
| `schedule plan.json [--start 15:00] [--json]` | a multi-step plan, with cumulative clock times |
| `done <id> <actual>` | record the real duration; the bias adapts |
| `quick` | regenerate `QUICK.md` from `rates.json` |

## How a number is made

```
seconds = (first_request + (requests - 1) x next_request + tokens / decode) x scale + tool seconds
```

`requests` comes from the tool calls, one per call (measured 0.97). `decode`, the two request overheads and
`scale` are fitted per model. `scale` is chosen so the median real turn comes out right, and the printed range
is the measured p10 to p90 of real turns.

Checked against 900 random measured turns from both agents: 80% within 2x, 90% within 3x, median ratio 0.93.
`tests/validate.py` replays it and prints the per-model breakdown.

## Layout

```
SKILL.md            what the agent reads: rules, anchors, traps, how to answer
QUICK.md            25 lines for subagents and small contexts, generated by `quick`
README.md           this file
timeplan.py         the CLI, one file, standard library only
data/rates.json     measured rates, regenerated by `calibrate`
data/files.jsonl    per-transcript cache, which is why calibrate is incremental
history.tsv         every estimate and the actual it produced
docs/RESEARCH.md    sources, external cross-checks, known gaps
tests/validate.py   replays real turns, reports how close the estimate lands
```

## Honest limits

- The numbers describe this machine, this provider, this scaffold and these tools. A different setup needs its own
  `calibrate`.
- Queueing and provider load are not modelled. They are what the range is for.
- Effort levels change thinking tokens and therefore time. Present in the transcripts, not yet split per model.
- Human time is an assumption. 1,500 tokens per hour, about one line of finished code per minute. The corpus holds
  no human timing, so `--human-rate` exists to argue with it.
- The model table needs a `calibrate` after a model appears or changes. A rate for a model that is not in `show` is
  unknown, not zero.
